# Транскрибатор

Сервис для разбора записей разговоров. Кидаешь аудиофайл — получаешь текст с разбивкой по спикерам и структурированный конспект: о чём говорили, что решили, кто что должен сделать, где риски.

Писал под свою задачу: разгребать записи созвонов и звонков, чтобы не переслушивать их вручную. Всё крутится локально, ни один байт аудио наружу не уходит — это было условием, поэтому никаких облачных API, только свои модели на своём железе.

## Как это работает

Файл проходит через четыре шага:

1. **Аудио.** Декодирую через ffmpeg, привожу к 16 кГц. Если запись пришла в 8 кГц (телефон) — чищу: полосовой фильтр 300–3400 Гц и мягкий шумодав, потом апсемплинг до 16 кГц.
2. **Распознавание.** Режу на куски по тишине (VAD) и прогоняю через Whisper. Движка два: `faster-whisper` и `whisper.cpp` — какой брать, решает конфиг (почему два — ниже).
3. **Спикеры.** Стерео-телефон, где оба канала не пустые — канал = спикер. Иначе моно и голосовой отпечаток (resemblyzer): считаю эмбеддинги кусков и кластеризую близкие.
4. **Разбор.** Собранный текст уходит в локальную LLM (Qwen2.5-7B через llama.cpp), она вытаскивает темы, решения, задачи и риски в структурированный JSON. Она же по контексту пытается определить настоящие имена участников.

Результат кладётся в `OUTPUTS/` (JSON) и в SQLite — историю потом видно в веб-морде.

### Про очередь

Обработка не мгновенная — файл на 40 минут молотится минутами. Поэтому `/api/transcribe` не ждёт результат, а ставит задачу в очередь и сразу возвращает `job_id`. Дальше опрашиваешь статус или смотришь в UI. Внутри — один воркер, задачи идут по одной (две модели в память одновременно не влезут, гонять параллельно смысла нет). Незаконченные при рестарте задачи подхватываются заново: загрузки лежат не в `/tmp`, а в `data/uploads`.

### Почему два движка Whisper

Деплой стоит на старой 1080 Ti (Pascal). Для LLM её хватает — llama.cpp собирается с CUDA и Qwen влезает в 11 ГБ. А вот `ctranslate2` (на нём faster-whisper) на Pascal с float16 еле шевелится, поэтому по умолчанию Whisper держу на CPU в int8. Если железо новее — переключаешь `whisper.device` и `whisper.compute_type`, код сам подберёт остальное. `whisper.cpp` оставлен как GPU-вариант для случаев, когда CPU не тянет; он собирается из исходников с CUDA и живёт в отдельном процессе, потому что его `libggml` конфликтует с llama.cpp в одном адресном пространстве.

### Длинные записи

Транскрипт длинного разговора не влезает в контекст LLM целиком. Тогда он режется на куски по границам реплик с нахлёстом, каждый пересказывается отдельно (map), потом частичные конспекты сводятся в один (reduce). Если и свод не влезает — сводится рекурсивно, попарно. За счёт этого объём итогового конспекта растёт с длиной записи, а не обрезается по лимиту.

## Стек

Python 3.11, FastAPI + uvicorn. Whisper (faster-whisper / whisper.cpp), resemblyzer для спикеров, Qwen2.5-7B-Instruct в GGUF через llama.cpp для разбора. Всё пакуется в Docker поверх образа с CUDA.

## Запуск в Docker

Нужно: Docker, nvidia-container-toolkit и GPU где-то на 11 ГБ VRAM.

```bash
docker compose up --build
```

Первый запуск качает модели (~5–6 ГБ), это надолго — дальше они лежат в `./models` и переиспользуются. Когда поднимется, открывай `http://localhost:8000` — там веб-интерфейс: загрузка файла и история разборов.

Тома вынесены наружу, чтобы правки кода и конфига не требовали пересборки образа, а история и БД переживали перезапуск (см. `docker-compose.yml`).

Если GPU нет или nvidia-container-toolkit не стоит — выкинь из `docker-compose.yml` блок `deploy.resources`, а в `config.yml` поставь `hardware.device: "cpu"` и `hardware.vram_gb: 0`. Работать будет, но разбор через LLM на CPU медленный.

## Запуск без Docker

Только если готов возиться со сборкой CUDA-колёс руками:

```bash
pip install -r requirements.txt
# llama-cpp-python обязательно с CUDA, иначе разбор уползёт на CPU и будет тормозить
CMAKE_ARGS="-DGGML_CUDA=on" pip install --force-reinstall --no-cache-dir llama-cpp-python
python run.py
```

Нужен ещё `ffmpeg` в системе — librosa декодирует им.

## Конфиг

Всё лежит в `config.yml` в корне. Путь можно переопределить переменной `CONFIG_PATH`.

Идея: ты описываешь железо, а программа сама раскидывает модели — сколько слоёв LLM класть на GPU, какой брать контекст, сколько потоков. Не устраивает авто-расчёт — прописываешь значение в `overrides`, оно перебьёт всё.

### server

| Ключ | Значения | Что делает |
|---|---|---|
| `host` | строка | Адрес, на котором слушает uvicorn. `0.0.0.0` — со всех интерфейсов. |
| `port` | число | Порт. Перебивается переменной `PORT`. |
| `log_level` | `critical` / `error` / `warning` / `info` / `debug` / `trace` | Уровень логов uvicorn. |

### hardware

Отсюда считается всё остальное. Заполняй честно — цифры берутся на веру.

| Ключ | Значения | Что делает |
|---|---|---|
| `device` | `auto` / `cuda` / `mps` / `cpu` | Основное устройство. `auto` — спросить у torch. Перебивается переменной `DEVICE`. |
| `vram_gb` | число | Сколько VRAM у карты. `0` если GPU нет. При `device: cuda` и `0` попробует спросить у драйвера. |
| `ram_gb` | число | Сколько оперативки отдаёшь под сервис. Используется для расчёта контекста, когда LLM на CPU. |
| `cpu_threads` | `auto` / число | Потоки для faster-whisper и llama.cpp. `auto` = `os.cpu_count()`. |

Что из этого выводится:

- `llm_gpu_layers`: `vram_gb >= 10` — вся модель на GPU (`-1`); `>= 6` — 20 слоёв; иначе `0` (только CPU). Считается **только если `device` = `cuda`**.
- `llm_context`: берётся память (VRAM если LLM на GPU, иначе RAM) минус ~5 ГБ на веса. Осталось `>= 12` ГБ — контекст 16384, `>= 5` — 8192, иначе 4096.
- `llm_threads` = `cpu_threads`.

### whisper

| Ключ | Значения | Что делает |
|---|---|---|
| `engine` | `faster` / `whispercpp` | Движок распознавания. `whispercpp` — GPU-вариант через отдельный процесс. |
| `ggml_repo` | HF-репозиторий | Откуда качать ggml-модель. Только при `engine: whispercpp`. |
| `ggml_model` | имя файла | Какой файл качать из этого репозитория. |
| `ggml_path` | путь | Куда положить и откуда грузить. Если файла нет — скачается при старте. |
| `hf_model` | HF-репозиторий | Русский дообученный Whisper через transformers. |
| `use_hf_model` | `true` / `false` | Пробовать ли `hf_model`. При `false` (и `engine: faster`) сразу берётся `fallback_model`. Если модель не загрузилась — тоже откат на `fallback_model`. |
| `fallback_model` | `tiny` / `base` / `small` / `medium` / `large-v3` | Модель faster-whisper. Перебивается переменной `WHISPER_MODEL`. |
| `device` | `auto` / `cuda` / `cpu` | Устройство для Whisper, **отдельно от LLM**. `auto` — как в `hardware.device`. Нужно, чтобы держать Whisper на CPU при живой GPU (см. про Pascal выше). |
| `compute_type` | `auto` / `int8` / `int8_float32` / `float16` / `float32` | Точность. `auto` на GPU: `float16` при compute capability >= 7, иначе `int8_float32`; на CPU — `int8`. |
| `beam_size` | число | Ширина луча при декодировании. Больше — точнее и медленнее. |

Приоритет выбора движка: `engine: whispercpp` → whisper.cpp; иначе `use_hf_model: true` → `hf_model` с откатом на `fallback_model`; иначе сразу `fallback_model`.

### llm

| Ключ | Значения | Что делает |
|---|---|---|
| `enabled` | `true` / `false` | Выключишь — будет только транскрипция, без конспекта и без имён спикеров. |
| `repo` | HF-репозиторий | Откуда качать GGUF. |
| `filename` | имя файла | Какой квант качать. |
| `local_path` | путь | Куда положить и откуда грузить. Если файла нет — скачается при старте. |

Модель меняется этими тремя полями. Промпты заточены под ChatML (`<|im_start|>`), так что без правки `_build_prompt` в `summarizer.py` берутся модели того же семейства (Qwen и совместимые).

### diarization

| Ключ | Значения | Что делает |
|---|---|---|
| `enabled` | `true` / `false` | Выключишь — вся моно-запись уедет на одного `SPEAKER_00`. На стерео-телефон не влияет, там разбор по каналам. |

### overrides

Перебивают авто-расчёт. `null` = считать самому.

| Ключ | Значения | Что делает |
|---|---|---|
| `llm_gpu_layers` | `null` / `-1` / `0` / число | Сколько слоёв LLM на GPU. `-1` — все, `0` — только CPU. |
| `llm_context` | `null` / число | Размер контекста LLM в токенах. |
| `llm_threads` | `null` / число | Потоки llama.cpp. |

**Частая засада.** `llm_gpu_layers` считается только при `hardware.device: cuda`. Если torch на твоей машине CUDA не видит (частый случай на старых картах и в WSL2), `device: auto` схлопнется в `cpu`, и LLM уедет на CPU, даже если llama.cpp собран с CUDA и прекрасно бы отработал на GPU. Симптом — в логах при старте:

```
[пересказ] ВНИМАНИЕ: LLM на CPU (llm_gpu_layers=0), пересказ будет медленным
```

Лечится явным `overrides.llm_gpu_layers: -1`.

### Переменные окружения

Перебивают конфиг, удобны для docker-compose.

| Переменная | Что перебивает |
|---|---|
| `CONFIG_PATH` | Путь к самому `config.yml` |
| `PORT` | `server.port` |
| `DEVICE` | `hardware.device` |
| `WHISPER_MODEL` | `whisper.fallback_model` |
| `DATA_DIR` | Папка с `jobs.db` и `uploads/`, по умолчанию `data` |
| `OUTPUT_DIR` | Папка с готовыми разборами, по умолчанию `OUTPUTS` |

## API

Форматы на вход: mp3, wav, m4a, ogg, flac, webm.

```bash
# поставить файл в очередь -> вернёт job_id
curl -F file=@запись.mp3 http://localhost:8000/api/transcribe

# статус задачи (когда done — внутри будет result)
curl http://localhost:8000/api/jobs/<job_id>

# что сейчас в очереди и в работе
curl http://localhost:8000/api/jobs

# готовые разборы из OUTPUTS
curl http://localhost:8000/api/history

# скачать конкретный разбор
curl "http://localhost:8000/api/history/download?path=<относительный путь из /api/history>"

# журнал (можно сузить до одной задачи: ?job_id=...)
curl http://localhost:8000/api/logs

# здоровье: какие модели поднялись
curl http://localhost:8000/api/health
```

Статусы задачи: `queued` → `processing` → `done` либо `error`.

Готовый результат выглядит так:

```json
{
  "language": "ru",
  "text": "полный текст записи",
  "segments": [
    {
      "start": 0.0,
      "end": 3.5,
      "text": "Добрый день",
      "speaker": "SPEAKER_00",
      "speaker_name": "Иван"
    }
  ],
  "speakers": {
    "SPEAKER_00": "все реплики первого одной строкой",
    "SPEAKER_01": "все реплики второго"
  },
  "speaker_names": { "SPEAKER_00": "Иван", "SPEAKER_01": null },
  "is_phone": false,
  "summary": {
    "title": "Тема обсуждения",
    "summary": "Подробное описание сути разговора",
    "topics": [
      {
        "title": "Название темы",
        "category": "technical",
        "points": ["Тезис с конкретикой"]
      }
    ],
    "decisions": [
      { "decision": "Что решено", "context": "При каком условии", "responsible": "Имя" }
    ],
    "action_items": [
      { "action": "Что сделать", "responsible": "Имя", "deadline": "01.02.2026" }
    ],
    "risks": [
      { "risk": "Описание риска", "impact": "Последствие" }
    ]
  }
}
```

`speaker_name` появляется в сегменте только если LLM смогла определить имя. `category` — одно из `technical`, `organizational`, `financial`, `other`. Если разбор не удался, в `summary` будет поле `error`.

## Структура

```
run.py                     — точка входа, поднимает uvicorn
config.yml                 — весь конфиг
Dockerfile, docker-compose.yml
transcriber/
  settings.py              — читает конфиг, раскидывает ресурсы по железу
  audio.py                 — декодирование, ресемплинг, чистка телефонии
  recognizer.py            — VAD-нарезка и распознавание
  whisper_worker.py        — whisper.cpp в отдельном процессе
  diarizer.py              — кластеризация голосовых отпечатков
  summarizer.py            — промпты и map-reduce разбора через LLM
  bootstrap.py             — докачка моделей при первом запуске
  jobstore.py              — очередь, история и журнал в SQLite
  storage.py               — запись результатов в OUTPUTS
  app.py                   — FastAPI, роуты, воркер очереди
  pipeline.py              — склейка всех шагов
  static/index.html        — веб-интерфейс
```

Рантайм-папки (в репозиторий не попадают): `models/` — веса, `data/` — `jobs.db` и загрузки, `OUTPUTS/` — готовые разборы.
